# Cloudflare Workers Migration Design

## Goal

Move the existing Instant Ramen Next.js full-stack application from Vercel to a separately deployed Cloudflare Worker using `@opennextjs/cloudflare`, while retaining Vercel as the production rollback target and leaving `instantramen.dev` unchanged until the Worker has been validated.

## Current Architecture

- Next.js 16 App Router application with route handlers, server rendering, server-side auth helpers, and `src/proxy.ts` routing/auth middleware.
- Supabase Auth for the Instant Ramen product experience.
- Supabase PostgreSQL accessed through Drizzle ORM and `postgres`.
- APIMart-backed image generation through server-only route handlers.
- ShipAny payment, storage, credits, admin, RBAC, and Better Auth infrastructure remains in place.
- Vercel remains the current production deployment and rollback target.

## Selected Approach

Use OpenNext's Cloudflare adapter to build one Cloudflare Worker named `instant-ramen`.

- Keep Next.js server behavior; do not use static export or Cloudflare Pages.
- Keep Supabase Auth, database schema, route handlers, server actions, payment, storage, and product code unchanged unless a verified Workers incompatibility requires a narrowly scoped fix.
- Continue using the Supabase Transaction Pooler. The runtime `DATABASE_URL` hostname must contain `pooler.supabase.com`.
- Do not add Hyperdrive, D1, or R2 incremental cache during this migration.
- Deploy first to the Worker's `workers.dev` URL. Do not add a custom domain or alter the current Vercel deployment.
- Preserve existing secrets in ignored local files and configure production secrets through Wrangler or the Cloudflare dashboard.

## Worker Configuration

`wrangler.jsonc` will use:

- Worker name `instant-ramen`.
- Entry point `.open-next/worker.js`.
- Static assets directory `.open-next/assets` with the `ASSETS` binding.
- Compatibility date `2026-07-13`.
- Compatibility flags `nodejs_compat` and `global_fetch_strictly_public`.
- A self-service binding required by OpenNext.
- Cloudflare Images binding for Next.js image optimization when generated by the official migration flow.

`open-next.config.ts` will use the default Cloudflare configuration without an R2 incremental-cache override.

## Database Compatibility

The project uses Drizzle, not Prisma. Prisma packages only appear as optional peer dependencies in the lockfile, so no Prisma Client migration is required.

The `postgres` package publishes a workerd-specific conditional export. It will be listed in `serverExternalPackages` so Wrangler can select the correct implementation. Cross-request connection reuse is unsafe in Workers, so the runtime must use per-request connections with `DB_SINGLETON_ENABLED=false` and `DB_MAX_CONNECTIONS=1`.

## Authentication and OAuth

Supabase Auth remains unchanged. The Worker runtime receives the same public Supabase URL/key values used by Vercel. After deployment, the new workers.dev callback URL must be added to Supabase Auth redirect allow-list before Google OAuth and email-link flows are tested there.

Google's OAuth callback remains the Supabase callback endpoint; only Supabase's application redirect allow-list needs the additional workers.dev application URL.

## Vercel Cleanup and Rollback

- Remove runtime use of Vercel Analytics and its dependency because it is deployment-specific and not part of product behavior.
- Keep the Vercel project active.
- Keep `vercel.json` during the parallel-run period as rollback configuration; it is ignored by Wrangler and does not affect Workers.
- Remove Vercel-specific branching in Next configuration only where OpenNext requires deterministic output.

## Validation Strategy

Validation proceeds in layers:

1. Existing Instant Ramen verification scripts and lint establish the application baseline.
2. `next build` verifies the standard Next.js build.
3. `opennextjs-cloudflare build` verifies adapter transformation and catches `src/proxy.ts`, Node API, package export, and bundle-size issues.
4. `opennextjs-cloudflare preview` runs the result in local workerd.
5. HTTP smoke tests cover homepage, callback routes, protected API behavior, static assets, and representative route handlers.
6. Auth, database writes, generation, upload, payment, and webhook tests are performed only when the corresponding safe test credentials and configuration are available.
7. Deploy to workers.dev, then repeat non-destructive production smoke tests. No DNS or custom-domain change is part of this migration.

## Failure and Rollback

- Any adapter or workerd incompatibility is fixed at the smallest failing boundary and re-tested before continuing.
- No production DNS changes are made.
- Vercel remains available throughout, so rollback requires no code or DNS action.
- If a core flow cannot be validated on workers.dev, the Worker remains a test deployment and the migration is reported as incomplete with the exact blocker.

## Non-Goals

- No UI or SEO changes.
- No Auth, credits, payment, admin, provider, or database redesign.
- No custom domain cutover.
- No Hyperdrive, D1, R2 incremental cache, or Cloudflare Pages migration.
